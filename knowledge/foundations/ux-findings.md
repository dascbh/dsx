# UX findings registry

> **When to consult**
> - After running any UX checker (`tools/ux-lint/text.mjs`, `screen.mjs`, `flow.mjs`): the result goes into the registry, never stays only in the conversation.
> - To know what is open, what the owner has already decided, what was fixed and what came back.
> - When setting up a project's no-regression lock (pre-commit or CI).

## Why it exists

A checker only finds. Without a durable registry, every run starts from scratch: what the owner chose is lost, nobody knows what was already fixed, and the same problem comes back unnoticed. The registry gives each finding a **stable id**, keeps the **owner's decision separate from the machine's result**, and computes the **status** by comparing runs.

## Where it lives (in the project, versioned)

```
.dsx/findings/<module>/
├── findings.json   # written by the tool on every register (do not edit by hand)
├── options.json    # written by the skill: 2–3 options per finding, with convention and recommendation
├── decisions.json  # written by the owner (page or chat → `findings.mjs decide/import`)
└── previews/       # generated by preview.mjs, outside git (see "Option previews")
```

The three are kept apart on purpose: registering again rewrites only `findings.json`; options and decisions survive.

## Format

`findings.json`
```json
{
  "module": "purchasing",
  "updated": "2026-10-03",
  "runs": [{ "at": "2026-10-03T12:00:00Z", "sources": ["text", "screen", "flow"], "commit": "602d8c2" }],
  "items": [{
    "id": "t-7f3a9c2e",              // family prefix (t | s | f | st | c) + 8 hex of the stable hash
    "family": "text",                // text (X) | screen (T) | flow (F) | states (S) | consistency (C)
    "rule": "X1",
    "severity": 2,                   // 0–4
    "element": "button",             // button | title | label | placeholder | tooltip | helper | alert | tab | menu | cell | accessible-name
    "text": "Remover da lista — {}",
    "variants": ["Remover da lista — Ricardo Almeida"],
    "screens": ["07-dlg-destinatarios"],
    "source": ["src/pages/orders/SuppliersDialog.tsx:80"],
    "message": "travessão no texto",
    "origin": "detector",            // detector (came from a checker) | review (manual review, via options)
    "first_seen": "2026-10-03", "last_seen": "2026-10-03",
    "present": true,                 // appeared in the last run of its family
    "fixed_at": null,                // day it last stopped appearing (keeps the memory for `regression`)
    "status": "open"                 // computed (see lifecycle)
  }],
  "deviations": [{ "id": "D3", "screens": ["modelo-editor"], "rules": ["T3"], "reason": "…", "decided_by": "owner", "until": null }]
}
```
`deviations` is the copy of the deviations declared in the `UX.md` at the last run that read it (`register --ux`, or `<root>/UX.md`). An item covered by one of them also carries `"deviation": { "id", "reason", "decided_by", "until" }` and status `accepted-deviation`.
Items of the `layout` family also carry `selectors` (path of the element measured in the capture, only to locate the preview; not part of the id). Items of the `screen` and `states` families also carry `region` (in `states`, the state + the region: `error · main`). `source` is relative to the project root; in the `screen`, `states` and `consistency` families it points to the capture (`.html:line`), in the others to the code.

**Stable id** = hash of `family | rule | anchor`, where the anchor is, in this order: the first code source without the line number (the file) + the normalized text (lowercase, single spaces, variable data replaced by `{}` — numbers, dates, times, amounts and, when there are `variants`, the part that changes between them); with no code source, the screen + region + text. Changing the file's line does not change the id; changing the text or the file does. Two declared adjustments: in the `flow` family the anchor is always the map's screen (or journey), because its evidence lists incoming transitions that change without the finding changing; and in the `text` and `consistency` families with no code source the anchor carries no screen, because the finding groups several screens (in `consistency`, the text is the function or concept — "excluir pedido" —, not the labels found). When the set of variants changes and the template text changes with it, the item inherits the registered id of the same family, rule and file that shares a variant with it.

`options.json`
```json
{ "items": { "t-7f3a9c2e": { "problem": "…", "options": [{ "text": "…", "convention": "Polaris: verbo + objeto", "note": "…" }], "recommended": { "index": 0, "why": "…" }, "case": "c16" } } }
```
`case` (optional) groups ids covered by the same case: the page shows a single card and the decision applies to all of them.
`preview` (optional, on each option) says how to show the option applied to the real screen; without it the family's default preview applies (see "Option previews").

`cases.json` (input of `findings.mjs options --from` and of `text-page.mjs`, written by the skill)
```json
{ "cases": [{ "id": "c16", "element": "button", "rule": "X2", "severity": 2, "text": "Remover da lista — Ana", "variants": [],
  "source": ["src/Dlg.tsx:80"], "screens": ["07-dlg"], "problem": "…",
  "options": [{ "text": "…", "convention": "Polaris: verbo + objeto", "note": "…" }], "recommended": { "index": 0, "why": "…" } }] }
```

## Option previews (before and after taken from the capture)

The decision page shows each case with the **image of today** and, on each option, the **after image**, cropped from the real capture of the screen (the pixels of the capture made from the code, never a mockup or a text-generated screen). The generator is `tools/ux-lint/preview.mjs` (or `audit.mjs --preview`); the page only reads the result.

**How it finds the element.** By what the finding already stores: text and variants (the template text becomes a pattern, `{}` matches any span), labels quoted in the message (T1, T7, L1, L6, L8), the start of the text (L7), the quoted example (T6), the attribute (`aria-label`, `title`, `placeholder`) when the text is not in pixels, and the **measured selector** of the L rules: `register` stores in `selectors` the path of the element `measure.mjs` measured, without it entering the id. Representative screen: the first screen of the case where the element appears (state captures of the same screen come after); in C2, the screen of the variant that stands out.

**Crop.** The whole dialog when the element is in a dialog; otherwise the surrounding card, section or group, up to ~720 px wide (more only when the element itself is wider), scale 1, always with the whole element inside. The "after" uses the same window as the "before" (the union of the crops of all options, with balloons and badges), so you can compare without moving your eyes. Before: element outlined in red; after: the changed or assembled element outlined in green (removal: dashed line where it was). Images in WebP (JPEG if the browser cannot encode WebP), quality ~70. A whole-screen finding shows the screen at half scale; with a state or region assembled on the screen, the open dialog is cropped at scale 1. L6 shows the whole window (the fold is the subject), with the fold line before and after.

**Always from the capture, never a mockup.** Everything the preview adds comes from some capture of the module: the **donor kit** (`tools/ux-lint/lib/preview-kit.mjs`, cached in `previews/kit.json`) walks the captures and stores, with the CSS each piece uses, the state block from `*.error.html`, `*.empty.html` and `*.loading.html` (what the state capture has and the base screen does not; with the alignment and spacing of the container that wrapped it), alerts by color, buttons by variant, panel, title, caption, chip, supporting text, search field, the kit's tooltip classes, the theme's error color (the `.Mui-error` rule) and the h1–h6 heading scale as the product uses it (mode of each level's size, with no lower level larger than the one above). When the capture itself has the piece, it comes from there; otherwise, from the kit.

**Operations** (the option's `preview` field: an object or a list applied in order):

| `op` | Effect on the capture's DOM | Fields |
|---|---|---|
| `text` | replaces the element's text (in a field, the placeholder); an icon-only button (found by its `aria-label`) becomes a screen reader annotation | `text`, with markers: `{self}` (today's text), `{part:0}`/`{part:1}` (blocks separated by a dash, `·` or `\|`), `{no-parens}` (without the parenthetical), `{context}` (nearest label before the element, lowercase) |
| `remove` | hides the element | — |
| `variant` | copies the classes of a button with the requested variant (from the capture, otherwise from the kit; never from a disabled button) | `variant`: `contained` \| `outlined` \| `text` |
| `move` | moves the element to the end or start of the action group and/or aligns the container; `region-top` lifts the element (or its button group) to the lowest point of the region that still fits above the first fold | `to`: `end` \| `start` \| `region-top`; `justify`: `flex-end` \| `flex-start` \| `center` \| `space-between`; `fold` (900) |
| `style` | inline CSS, only layout and typography properties from the closed list (`max-width`, `width`, `margin*`, `padding*`, `gap`, `font-size`, `font-weight`, `line-height`, `text-align`, `justify-content`, `align-items`, `flex-*`, `order`, `display`…; never color). Value `theme:h1`…`theme:h6` uses the kit's heading scale; `theme:self`, the heading's own level | `css`: `{ "max-width": "60ch" }` |
| `align` | aligns the left edge of the located items (the whole field, with label): stacked, to the first one's; in rows, to the columns of the first row, keeping the right edge | `mode`: `auto` \| `left` \| `columns` |
| `replace-text-many` | replaces several spans at once in the element (or on the screen) and tidies the leftover punctuation | `pairs`: `[{ "from", "to" }]` (empty `to` removes the span); `scope`: `element` \| `screen` |
| `insert` | inserts a copy of a real element before/after/inside the target, with text | `like`: `chip` \| `helper` \| `caption` \| `search-field` \| `panel` \| `alert-info` \| `alert-warning` \| `alert-success`, or `from` (capture) + `source` (selector); `position`: `before` \| `after` \| `prepend` \| `append`; `text`; `placeholder` |
| `wrap` | puts the target inside a copy of the capture's panel/card, with a title | `title` |
| `annotate` | balloon attached to the element: "Leitor de tela: «…»" (accessible name), the tooltip with the kit's tooltip classes, or a note | `kind`: `screen-reader` \| `tooltip` \| `hint`; `text` |
| `badge` | today's image with a badge in the corner of the crop; not a failure | `text` (default "Sem mudança") |
| `synthesize-state` | assembles on the screen a state no capture shows (see below) | `state`; `title`, `text`, `action` replace the default texts |
| `synthesize-region` | inserts the missing archetype region as a container (copy of the capture's panel) with a title; `search-bar` becomes a copy of the search field | `region`, `title` |
| `example` | changes nothing: shows as a reference the capture of another screen or state that already does it right | `screen`: `02-orders.error` |
| `none` | no preview; the page says why | `reason` |

Any operation accepts `selector` to target another element of the capture and `targets` (`all`, `all-but-last`, `all-but-first` or the index) when the locator finds several. Example: `{ "text": "Ver histórico, com selo \"1\"", "preview": [{ "op": "text", "text": "Ver histórico" }, { "op": "insert", "like": "chip", "position": "after", "text": "1" }] }`.

**State assembled on the screen** (`synthesize-state`, default for S1). The recipe (`STATE_RECIPES` in `lib/preview-spec.mjs`) says where and with what: `replace` swaps the content below the header (title and tabs stay) for the state block — no access, invalid or expired link, unavailable, already answered; `replace-data` swaps only the table or list (filters stay) — loading, empty, empty by filter, no data in the period, load error; `banner` inserts the alert of the right color at the top of the content (in a dialog, above the action footer) — error and no access in a dialog, processing, partial, outdated, conflict, saved, not saved, read-only, recovered draft; `field-error` marks the required field with the kit's error classes (`Mui-error`) and the theme's error color read from the capture's CSS, with the error text below. With no red alert in any capture, the error in a dialog copies an alert from the capture and paints it with the theme's error color (dark text, light background, border and icon in the color). Default texts follow the UX.md feedback policy: no access says who grants it, error says what to do; the option's text beats the default. The caption is "Proposta montada com componentes da própria tela".

**Default preview** (option without `preview`). The quoted forms below are the pt-BR option phrasings the parser matches, kept verbatim:
- **Text** (`text`): an option with ready text becomes `text` (including a sentence with inner quotes, such as “Criar pedido”); `"A" → "B"` applies B; `Rótulo: texto` applies the text; `(remover)` becomes `remove`; "Manter…" becomes a `badge` "Sem mudança"; an option that lists texts of several elements (`A · B · C`) applies the span with the most words in common (5-letter stem) or, with no word in common, the one that repeats the numbers of today's text, and lastly the first one, with a note; an instruction with the text in quotes after the element name (`Título "…"`, `texto "…"` after `;`) replaces only the main text and warns; `X, com apoio "Y"` inserts the supporting text, `com selo "Y"` inserts the chip, `com nome acessível "Y"` annotates the screen reader; other structural instructions get no preview (declare `preview`). An accessible name becomes a screen reader `annotate` and a tooltip becomes a tooltip `annotate`, with today's name or tooltip in the "before".
- **By rule**: **L1** → `move` (`to: end`, `justify: flex-end`); **L3** → `style` with `theme:self` on the cited headings; **L4** → `align`; **L6** → `move` `region-top`; **L7** → `style` (`max-width: 60ch`, about 72 characters: `ch` is the width of the zero, larger than the average letter); **L8** → `style` `min-width`/`min-height` 24 px (44 if the message asks for it); **L9** → `synthesize-region`; **C1** → `text` with the first cited label, on the other screen; **C2** → the majority `variant`; **T1** → `variant` `outlined` on the region's primaries except the last; **T3** → the most prominent text at the top (editable title included) on the h1 scale + annotation "Título, nível 1"; **T6** → `replace-text-many` replacing the term with a common word (`SES` → "e-mail"; hash and `sha256` are removed); **T7** and **X6** without an object → `text` `"<botão> {context}"`; **X2** → first block in the title and the second as supporting text below; long **X6** → first block; **X9** → without the parenthetical; **S1** → `synthesize-state`; **flow F1, F2, F5** → mini before/after SVG diagram of the screen's transitions in the map (no browser): new exit, declared journey, way back.
- **Behavior and structure options** (review rules `H1`…`H10`, `DP`, `IA`, `A11Y`, `LAW`): the option text is read as screen text only in the explicit forms above (`"A" → "B"`, `Label: text`, element + quoted text, a whole quoted text); any other option is an instruction and gets no derived preview — the page says so in its language. In every family, an unquoted text longer than a label (over 60 characters, or twice today's longest text) is never pasted into a button, tab, menu, label, title, cell or chip. A wrong "after" image is worse than none: declare `preview` (`synthesize-state`, `insert`, `variant`…) when the change can be shown.
- A position or style operation that changes nothing in the capture (`move`/`style`/`align` with the element already that way) shows today's image with the badge "Já está assim nesta tela".

**Type caption.** Below each "after" the page states the type (pt-BR page labels): "Texto trocado", "Elemento removido", "Peso do botão trocado", "Elemento movido", "Estilo ajustado", "Tamanho na escala do tema", "Proposta montada com componentes da própria tela", "Anotação: leitor de tela", "Anotação: dica", "Sem mudança", "Já está assim nesta tela", "Exemplo de outra tela", "Diagrama do fluxo" (comes from `kind_label` in the manifest).

**Case without options** (screen, layout, states, flow families) shows, next to "Hoje", the **fix indicated by the rule** with the same default preview. It is not a decision option: the form stays the same.

**Where it lives** (generated, outside git: ignore `.dsx/findings/*/previews/`):
```
.dsx/findings/<module>/previews/
├── previews.json          # manifest: case → before, after[] (option, applied op, description, kind_label) or failed with the reason
├── kit.json               # the module's donors taken from the captures (cache)
└── <hash>.before.webp …   # images; screen-<hash>.webp for the whole screen; .svg for flow
```
Cache: the case hash combines the previews version, the code that runs in the capture (`lib/preview-runtime.mjs`), the captures involved, the locator, the operations and, when the operation uses the kit, the set of the module's captures; a case with a variant without a preview is always redone; a case with the same hash and files present is not redone, and a file no case uses is deleted. The page marks as outdated a preview whose capture changed after it was generated.

**Paginated page.** The page comes out in several files, each self-contained (images embedded in base64): `<output>.html` (index and page 1), `<output>-2.html`… with at most ~10 MB and 60 cases per file (whichever comes first), in group order (a large group spans pages). Navigation at the top and bottom. Choices are kept in the browser's `localStorage` (key by module and registry version; the page works without it) and "Copiar decisões" on any page copies those of all pages; the top shows "N decididos de M". `--preview-files` references the images in `previews/` instead of embedding them (the tool warns if pages + images exceed 255 files).

## Inputs: the checkers' `--json` output

| Checker | Shape | Fields the registry reads |
|---|---|---|
| `text.mjs --screens … --code … --json` | `{ summary, ranking, findings: [group], screens: [per screen] }` | per group: `rule`, `severity`, `text`, `variants`, `types`, `screens`, `message`, `source.occurrences[{file, line}]`; `probable_data: true` when the piece came from the data (severity 0) |
| `screen.mjs --json` | `{ summary, screens: [{ file, dialog_open, findings: [{ rule, severity, region, message, evidence }] }] }` | all |
| `flow.mjs --json` | `{ file, findings: [{ rule, severity, screen, message, evidence: [] }], summary }` (or a list, with several maps) | all |

`types` (element type in the text checker): `title`, `button`, `tab`, `label`, `placeholder`, `helper`, `alert`, `accessible-name`, `tooltip`, `empty-value`.

**Name transition (2026-10).** Up to version 0.4 the checkers were called `texto.mjs`, `tela.mjs` and `fluxo.mjs`, emitted keys in Portuguese (`achados`, `regra`, `severidade`, `telas`, `origem.ocorrencias[{arquivo, linha}]`…) and options came in `casos.json` (`casos`, `elemento`, `opcoes[{texto, convencao, nota}]`, `recomendada{indice, porque}`). The registry still **reads** those old JSON files and also the camelCase keys of an intermediate version (`probableData`, `byRule`, `dialogOpen`…), and warns "nome antigo, renomeie para X" in the case of `casos.json`; the tools only write the new names. Old flags (`--telas`, `--codigo`, `--ignorar`, `--falhar-em`, `--produto`, `--cor`, `--titulo`, `--arquetipos`) keep working as aliases: the tool swaps in the new name and warns "nome antigo, use --X" (single table in `tools/lib/legacy-cli.mjs`). Full table: `docs/renames-2026-10.md`.

**Key convention.** Every JSON (`--json` outputs, `findings.json`, `options.json`, `decisions.json`, `cases.json`, maps) uses **snake_case** (`by_rule`, `probable_data`, `first_seen`); YAML front matter (the `UX.md`) uses **kebab-case** (`primary-position`). Ids used as a value or as a key of an id map (`accessible-name`, `X10`) stay as they are.

`decisions.json`
```json
{ "items": { "t-7f3a9c2e": { "choice": 0, "by": "owner", "at": "2026-10-03", "reason": null } } }
```
`choice`: index of the option, `"ignore"` (requires `reason`) or `"free"` with `text`.

## Lifecycle (computed status, never written by hand)

| Status | When |
|---|---|
| `open` | present in the last run, no decision |
| `decided` | present, with an option or free-text decision (not yet applied) |
| `ignored` | `ignore` decision with a reason (does not count toward the lock) |
| `accepted-deviation` | present, and covered by a current deviation in the `deviations` block of the `UX.md` (rule in `rules`, all screens in `screens`, `until` not expired). Counts neither as open nor toward the lock; shown on the page with the reason |
| `fixed` | did not appear in the last run of its family, after having appeared |
| `regression` | appeared again after `fixed` |

Precedence: `ignored` (owner's decision) → `fixed` → `accepted-deviation` → `regression` → `decided` → `open`. The deviation is recomputed on every register: if it leaves the `UX.md`, expires or stops listing the rule or the screen, the finding goes back to `open` (or `regression`). The difference from `ignored`: the deviation is a product decision written in the `UX.md`, valid for every finding of the same rule on those screens, including those that have not appeared yet; `ignore` is the decision about a single id.

Manual review items (`origin: "review"`) are not seen by the checkers: a run never marks them as absent, so they stay `open`, `decided` or `ignored` until someone reviews again.

## No-regression lock (`findings.mjs check`)

Runs the same checkers (or reads the JSON of a run) and compares with the registry:
- **new finding** (id that does not exist in the registry) with severity ≥ `--min` (default 2) → fails;
- **regression** → fails;
- findings already registered and open → tolerated (the debt is known), but shown in the summary;
- findings covered by a deviation declared in the `UX.md` (read from `--ux` or from `<root>/UX.md`) → pass, even if new, and appear in the "covered by a declared deviation" count.

That way the product only gets better: nothing new comes in worse, and what was fixed does not come back.

## Workflow

1. **Detect**: run `text.mjs`/`screen.mjs`/`flow.mjs` with `--json`.
2. **Register**: `node tools/ux-lint/findings.mjs register --module <m> --text t.json --screen s.json --flow f.json --root <repo> [--ux UX.md]` (the `UX.md` provides the accepted deviations).
3. **Propose**: the skill writes the options (`findings.mjs options --module <m> --from cases.json`); a case that matches no finding comes in as a manual review item.
4. **Preview**: `preview.mjs` (or `audit.mjs --preview`) crops before and after for each case from the captures.
5. **Decide**: the owner chooses on the page (`findings.mjs page`, which generates the form and a decisions JSON to paste) or in the chat; `findings.mjs import` / `decide` writes to `decisions.json`.
6. **Apply**: fix at the source (`file:line`), one decision at a time or in bulk.
7. **Confirm**: detect and register again — what disappeared becomes `fixed`; what came back, `regression`.
8. **Lock**: `findings.mjs check` in pre-commit or CI.

## Checklist

- [ ] Every UX checker result goes into `.dsx/findings/<module>/` (not into a temporary folder or only in the conversation).
- [ ] Owner decisions written to `decisions.json`, with who and when; `ignore` always with a reason.
- [ ] A product deviation (valid for one rule across several screens) declared in the `deviations` block of the `UX.md`, not as several `ignore`s.
- [ ] After fixing, register again and check for the `fixed` status.
- [ ] `findings.mjs check` wired into the project's pre-commit or CI.
