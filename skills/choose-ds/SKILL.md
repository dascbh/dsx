# Choose and build the design system

> **DSX root:** two levels above this skill's base directory. Paths under `knowledge/`, `references/`, `tools/` are relative to it.

Reference: `knowledge/design-system/choosing-a-design-system.md` (register, evaluation, presentation, construction). Format and official linter: `knowledge/design-system/design-md.md`.

**Principle:** a ready-made reference speeds things up, but only after three filters, in this order: **the product's register** (what it is used for), **objective evaluation** (does the file work?) and **adaptation** (it becomes *this* product's system, not a copy).

## 1. Context (before looking at styles)

Survey, from the code, the maps (`.dsx/maps/`) or by asking the minimum:
- persona and main task; frequency and duration of use;
- **register**: `operational`, `consumer`, `editorial`, `brand` or `experimental` (table in the knowledge file). IF the project has a `UX.md` → THEN use its `product.register` and `product.density` (the screens' archetypes already depend on that register); choosing a different register here is a major change to `UX.md` (skill `ux-md`, `version` 2.0.0) and needs the owner;
- target density, platform (desktop, mobile), light/dark theme (`--theme light|dark`);
- what is already fixed: brand color, licensed font, existing components;
- accessibility requirements beyond AA.
With no declared problem, go through the `discovery` skill first.

## 2. Screening in the catalog

```bash
node tools/references.mjs search --register <register> --use "<persona and domain words>" --curated --n 8
node tools/references.mjs search --register <register> --use "<...>" --n 15          # the non-curated ones too
```
- Curated entries (`references/design-md/curated.json`) already have a score (`score`) and defects (`contrast_failures`, `errors`, `warnings`). Outside them, download the candidate: `node tools/references.mjs fetch <slug>`.
- Discard `experimental` for an operational product; be wary of a style whose only use case is "landing page".

## 3. Objective evaluation of each candidate

```bash
node tools/references.mjs evaluate references/design-md/designmd-app/<slug>.md
npx -y @google/design.md lint references/design-md/designmd-app/<slug>.md
```
List per option: score, failed contrast (component and ratio), missing components, warnings from the official linter. Contrast < 4.5:1 → the option only enters as "adaptable", with the proposed fix.

## 4. Present 3 + 1

- Three options within the register and **one contrasting option**. For each: what it favors, what it worsens, score/defects, adaptation effort, and the credit (designmd.app, CC BY 4.0).
- **Each one becomes a design option** (skill `design-lab`): `node tools/design-md/lab.mjs add <name> --from-reference <slug>` (or `--variant-of current --set …` for an adaptation of the current file). `lab.mjs list` gives score, problems, readable text and what changes for all of them at once.
- **Show it in the product** (the screens shown cover the main archetypes in `UX.md`, when it exists — a list, a detail or editor, a dialog —, because a theme breaks in different ways on each type of screen):
  - Project with screens and capture from code (skill `capture-from-code`): **render the real screens with each option's theme** — one theme over the product's theme, built from the option's DESIGN.md by the theme adapter (palette, font, radius, spacing and the fixed colors of common components). `node tools/design-md/lab.mjs compare <a> <b> <c> <d> --screens <4–6 screens> --out compare.html` captures each option and writes the static comparison page (Current + options in columns, zoom, "Copy decision"). Pick screens that cover the main archetypes, not the whole product. Optionally send the same captures to Stitch, one row per option (`arrange-canvas.mjs --rows`).
  - App running locally: the live switcher (`design-lab`, live mode) shows the same options in the real app with `?ds=<name>`.
  - **Do not use `apply_design_system` on screens captured from code**: they carry the real CSS with fixed colors, and the tool barely changes anything (tested on 2026-10-02: only one badge changed). It works on screens generated by Stitch itself.
  - Project without screens: generate the same key screen with each design system (skill `stitch`, Generate mode) and critique each one (Critique mode).
- **Critique each option on the screens, not in the file:** what breaks in real use (e.g. a dark theme turns a document's sheet dark; a neutral palette erases the color distinction between field states) weighs more than the score. Also note what did **not** change with the theme: those are fixed colors in the product's code, design-system debt to record.
- **Stop and ask the product owner to choose.** Do not choose for them.

## 5. Build the project's DESIGN.md

The chosen option is promoted with `node tools/design-md/lab.mjs promote <name>` (gates first, previous file kept) after it is adapted. Follow "Building: from the reference to the project's DESIGN.md" in the knowledge file (copy as a draft with credit → swap the identity → DSX roles → fix defects → the product's prose). Then the `design-md` skill (Mode C) evaluates the result and the `tokens` skill generates ramps and scales.

## 6. Validate and sync

```bash
node tools/lint-design-md.mjs DESIGN.md
npx -y @google/design.md lint DESIGN.md
npx -y @google/design.md export --format dtcg DESIGN.md > tokens.dtcg.json   # if the project uses DTCG
```
Take it to Stitch (skill `stitch`, Sync mode) and check with `node tools/stitch/design-system.mjs check`.

## Output

```
Register: <register> · persona: <...> · fixed: <color/font/…>
Options: A <slug> (score, defects) · B · C · contrasting D  → .dsx/design-options/<name>.md
Seen in: <comparison page / live switcher / Stitch project, screens>
Owner's choice: <slug> → project's DESIGN.md (credit kept)
Gates: DSX <passed/failed> · official <errors/warnings> · Stitch <conforming/divergent>
```
