# Sandbox

> **DSX root:** two levels above this skill's folder. `templates/`, `tools/`, `knowledge/`, `docs/` are relative to it; paths without a prefix (`.dsx/`, `src/`, `DESIGN.md`) belong to the project.

## What it is

```
official code (src/, public/, DESIGN.md, .dsx/design-options, capture data)
   │ sync (copy + base of hashes)                         ▲ apply <paths> (3-way check, gates, no commit)
   ▼                                                      │
<package>/sandbox/mirror/  ── edited by agents ──▶  status · diff · discard
   │
   ▼ separate Vite build (vite.sandbox.config.ts): real entry from the mirror
   ├─ auth module swapped by a fake one (personas, unsigned fake JWT)
   ├─ API base env vars → /__dsx/<base> answered by mocks (fake-api router) under a scenario
   ├─ everything else intercepted: fetch, XHR, iframe src, WebSocket (same host only), sendBeacon → blocked + logged
   ├─ CSP connect-src 'self' (+ local WebSocket for HMR); dev server fs.allow = sandbox folder + node_modules
   └─ panel (data-dsx-sandbox): scenario, persona, latency, request log; live design-lab manifest from the mirror
```

Phase 1 supports **Vite + React**. The harness lives in `<package>/sandbox/` and is versioned (mocks, fake auth, config); the mirror and the build (`sandbox/mirror/`, `sandbox/dist/`) are local and ignored.

Commands: `node tools/sandbox/sandbox.mjs <command> --root <project>` (the header of `tools/sandbox/sandbox.mjs` lists them all). Exit codes: `0` ok · `1` gate (conflict, isolation, lint) · `2` usage · `3` setup missing (config, mirror, Vite).

## Rules

- **Never edit the official code to make the sandbox work.** Everything goes in the harness (`sandbox/mocks`, `sandbox/auth`, `.dsx/config.json` → `sandbox`). The only official edits are the ignore patches that `init --write` shows first.
- **Sandbox edits go only in the mirror** (`<package>/sandbox/mirror/<same relative path>`), and reach the real code only through `apply` on paths the user approved. `apply` never commits.
- **No real host, ever.** No credentials, no real tokens, no staging URL in mocks or config. Fictional data only (same rule as capture: no real names, clients or documents). `build` runs `isolation-check`; a failure blocks using that build.
- **The official build must not carry the sandbox**: run `bundle-check <official dist>` in CI or before release.
- Panel labels follow the product language through `sandbox.labels`; code, keys, scenarios and file names stay in English.

## Procedure

### 1. Set up (once per project)

1. `sandbox.mjs init --dry-run --root <project>` — nothing is written. Show the user what was detected: package, entry, plugins (and those left out: plugins defined inside the Vite config are usually production guards), auth module and its exports, the token claims the code reads (personas are shaped with them), API bases, identity settings to blank, fictitious hosts (a host the code validates by format gets a value that passes it), real hosts, routes called by providers/layout (proposed as `exempt`), the denial code the code branches on (proposed as the forbidden answer), mirrored items (including the Markdown design docs DESIGN.md/UX.md cite outside the front package, and test fixtures; never the package itself or the root), files to create and the **patches** (git, eslint, vitest, npm scripts).
   - A `WARNING BLOCKING` line means the sandbox would not work as proposed (e.g. a validated host with no passing value): fix that key in the block before going on.
2. Fix wrong guesses by passing `--package <dir>` or editing the block after writing. On the user's OK: `sandbox.mjs init --write`. A later `init` keeps the team's block and only adds newly detected mirror items.
3. **Existing harness** not generated by DSX in the sandbox folder: `--write` is refused. See "Migrating a harness".
4. Fill the fake auth (`sandbox/auth/<module>`): it must export **the same names and shapes** as the real module (the header lists them). Keep the session derived from `currentPersona()`.
5. Write mocks (`sandbox/mocks/<module>.ts`, imported in `mocks/index.ts`) from the API the screens use: `route('GET api:/orders/:id', (ctx) => ok(...))`. Handlers are fixed answers, queues or functions of `ctx` (`method`, `base`, `path`, `params`, `query`, `body`, `headers`, `scenario`) and may keep state in module variables (a created record shows up in the next list). Helpers in `runtime/fake-api.ts`: `ok(data)` (adapt it to the project's envelope), `fail(status, code, message)`, `respond(status, body, headers?)`, `noContent()`, `newId(prefix)`, `PENDING`; a function returning a plain value answers 200 with it, returning nothing answers 204. Reuse the capture data (`*.data.ts`) when it exists — the mirror carries it, and legacy files importing `./environment` are redirected to the fake API automatically. Every request without a mock shows as `no-mock` in the panel log: that list is the to-do.
6. Personas (`sandbox.personas`): one per role that changes what the UI shows; claims shaped like the real token (init uses the claim names and group values the code compares; check them).
7. `sandbox.mjs build` → must print `Isolation: OK`. Then `sandbox.mjs dev` and open the printed URL.

### 2. Work in the sandbox

1. `sandbox.mjs sync` (or `dev`, which creates the mirror when missing). Before a session, `status`: official changes not in the mirror are brought in by `sync`; conflicts are kept on the sandbox side.
2. Edit files in the mirror. Vite reloads. Check every relevant scenario from the panel or the URL (`?scenario=empty&persona=member`): normal → success, empty → empty, slow → loading, error → error, forbidden → no-access. Routes that must keep working under error/forbidden (session, the shell's selectors, feature flags) go in `sandbox.exempt` (`"GET api:/path"`, `"api:/path"` or `"/path"`; `:param` and `*` match one segment). When the app only shows its no-access state for a specific error code or envelope, set `sandbox.scenario_responses.forbidden` (and `.error`) to `{ "status": 403, "body": … }`.
3. DESIGN.md options: edit `DESIGN.md` or `.dsx/design-options/*.md` **in the mirror**; the design-lab switcher reloads with the change (skill `design-lab` for the options themselves).
4. Review with `status` and `diff [<path>…]`. Throw away what failed with `discard <path>…`.

### 3. Bring it back

1. Show the user `status` and the `diff` of what is proposed. Apply only approved paths: `sandbox.mjs apply <path>…` (or `--all` when everything was approved).
2. **Conflict** (official changed too): apply refuses everything selected. Merge by hand in the mirror using `diff`, then `apply --force` on those paths.
3. Gates run after apply: raw values on applied UI files, `lint-design-md`/`lint-ux-md` when those files changed, and the design-lab manifest refresh when DESIGN.md or options changed. Exit 1 = fix before going on.
4. Then the usual `build-ui` checks on the touched screens (captures, states, UX.md drift) and the user commits.

## Migrating a harness

When the project already has a hand-made sandbox in the same folder:

1. `init --dry-run` lists what would move and what stays. `init --write --migrate` moves the old harness's versioned files to `.dsx/sandbox-previous-<date>/` (outside the front package, so its lint and tests ignore it), leaves git-ignored folders in place (its old mirror and build: delete them by hand) and writes the new harness. Nothing is deleted.
2. Port, in this order: the fake auth (same exports as the real module), the mocks (rename the old helpers to the `fake-api` ones; the route syntax `METHOD base:/path/:param` and function handlers with a context are the same model, so a codemod of names usually suffices), personas, exempt routes and scenario answers into the block.
3. `sandbox.mjs build` (Isolation OK) and `dev`; walk the screens per scenario and compare with the old harness before deleting `.dsx/sandbox-previous-<date>/`.
4. Scripts: on `--migrate`, existing `sandbox*` scripts that would break are replaced (the dry run shows before → after) and old ones without a DSX equivalent are listed for removal by hand. Git-ignored leftovers stay in the harness folder; a leftover in the new mirror's place makes `sync` stop until it is deleted.
5. The npm scripts run `<package>/sandbox/cli.mjs`, which finds the DSX at `sandbox.dsx_root` (written by init); env `DSX_ROOT` overrides it on a machine where the DSX lives elsewhere.

## Config (`.dsx/config.json` → `sandbox`)

Written by `init`, owned by the team afterwards (a later `init` keeps it). Main keys: `package`, `dir`, `mirror`, `items` + `filters` (what is mirrored), `synthetic` (mirror-only files), `entry`, `aliases`, `swaps` (real module → replacement), `redirects`, `api_bases` (`{name: ENV_VAR}`), `env` (blanked identity settings, fictitious hosts), `real_hosts` (what the build must never contain), `exempt`, `scenario_responses`, `personas`, `default_persona`, `default_scenario`, `latency_ms`, `slow_ms`, `storage_key` (`dsx-sandbox`), `labels`, `ports`, `csp_extra`. Reference: `docs/project-paths.md`.

## Deliver

- After setup: the `init` summary, `Isolation: OK`, the dev URL and the `no-mock` list still open.
- After a session: what changed (`status`), the scenarios checked per screen, and what was applied, with gate results. Never "done" with a failed gate or an un-applied change the user believes is in the code.
