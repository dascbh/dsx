# Build UI inside the system

> **DSX root:** two levels above this skill's base directory. All `knowledge/`, `patterns/`, `tools/`, `templates/` paths below are relative to it. Paths without a prefix (`DESIGN.md`, `UX.md`, `src/`) belong to the user's project.

The goal is not "a pretty screen"; it is **a screen that looks like it was made by the same team that made the rest of the product** and that works in every state, for everyone.

## 0. Preconditions

1. Look for `DESIGN.md` at the project root. **If it does not exist**, stop and run the `init` skill (or `design-md` in "extract from code" mode). Building with no visual source is the main cause of drift.
2. Look for `UX.md` at the project root. **If it does not exist**, stop and run the `init` skill (or `ux-md` in Mode A, "extract from code"): building without knowing what type of screen it is, where the primary action sits and which states are mandatory is the main cause of screens of the same type diverging. **Before designing, read the screen's archetype**: its row in the "Screen archetypes" section (and the D… deviations that cite it), the card `archetypes/<id>.md` (regions, primary action, states, variations), the position and limit of primary actions, the confirmation and feedback policy, the mandatory states and the forbidden terms. Screen with no archetype in the table: propose one and record it in `UX.md` before building (skill `ux-md`); to choose between arrangements, skill `arrange-screen`.
3. Find the token source (CSS variables, Tailwind theme, `tokens/*.json`, MUI theme…) and the shared components folder. Note the paths.
4. If there are project maps (`.dsx/maps/`, generated by the `map-ux` skill), read the relevant ones before designing: `flows.json` (where the screen is reached from and where it leads), `tasks.json` (steps and dependencies), `domain.json` (where the data comes from, cardinalities), `journey.json` (persona and moment). Items under `uncertain` are not facts — confirm with the user or run `confirm-maps`.
5. If the project keeps the Figma cycle (`design/figma-sync.md` exists) and the turn is `design`, **do not change screens that are being refined** without agreeing first — the change will collide with the next round trip (skill `figma-turn`). When you finish with turn `code`, the screens you touched go into the next incremental re-mirror (`figma-mirror`).
6. If the screen comes from a chosen variation (skill `rethink-ux`, `.dsx/variations/<module>/<flow>/decision.json`), build the decided variant (or the per-axis composition) from its manifest and its test code: the code in `tests/…/variants/` is a composition reference using the same components, never pasted into production. Update `UX.md` (archetype, deviation, flow) in the same commit and check in the re-audit that the `resolves` ids became `fixed`.
7. If the screen comes from Stitch (`.stitch/designs/<slug>.html|png`), it is a **layout and content reference**, not code: follow the "Bring" mode of the `stitch` skill (colors mapped by role, the project's components, fixes the critique pointed out).
8. If the task is a new feature without a defined problem ("make a screen for X"), ask **for whom** and **which task** the screen solves before designing. One sentence is enough.

## 0b. Product pipeline contract (Forward)

When the work belongs to a Forward cycle (`cycles/C-<n>/plan.md` exists), the UI realizes a contract written before it (`knowledge/foundations/product-pipeline-ux.md`):

1. **Read the blueprint** of the front demand: `specs/<demand-id>/design/intended-model.md` (actors, jobs, primary actions and consequences, acceptance scenarios) and, when present, `flow.md` and `ia.md`. UI is the realization of this contract, not the source of the job. A blueprint gap (missing state, screen without requirement) goes back to its owner; do not improvise it in code. Check before building: `node <DSX>/tools/ux-lint/blueprint.mjs check --design specs/<demand-id>/design --no-captures`.
2. **Read the UI/UX criteria** of the plan (`node <DSX>/tools/ux-lint/criteria.mjs list cycles/C-<n>/plan.md`). Build toward the declared targets and counter-metrics; never edit them (the plan is frozen at sign-off).
3. **Internal criticism before code.** Write six short entries — strongest counter-case, unsupported claims, failure/recovery scenarios, accessibility, domain/data contradictions, security/operational risks — each resolved (what you changed) or turned into an explicit limitation or measurement task. Put it in the demand's notes on `cycles/C-<n>/board.md` (or in the variations manifest's `critique` when the screen comes from `rethink-ux`). It never replaces the isolated review (`ux-reviewer`, Forward `fde-review`).
4. **After UI**, verify the realized journey: recapture, then `blueprint.mjs check --design specs/<demand-id>/design --module <m> [--journey <id>]` (no orphans both ways, DOM-5) and `audit.mjs --module <m> --root . --criteria cycles/C-<n>/plan.md --criteria-out evals/ux/C-<n>-criteria.json`. Report UI quality, UX quality and DS adherence as separate verdicts; `unknown` stays unknown.

## 1. Discovery before writing code

Do this inventory **before** creating any file:

- [ ] Which existing components solve parts of the screen? (search by name: `Button`, `Input`, `Dialog`, `Table`, `EmptyState`, `Skeleton`, `Toast`…)
- [ ] Is there a similar screen in the product? Open it: it defines the layout, action positions and density you should repeat.
- [ ] Which interaction decisions does the screen require? For each, consult the catalog `patterns/README.md` (or `patterns/index.json`) — examples: modal or page? toast or inline? pagination or "load more"? table or cards? when to validate the field?

Record the decisions in a short list (`decision → pattern applied`). It goes into the final report.

## 2. Construction rules

**Tokens**
- Use **only semantic tokens** (`--color-text-primary`, `--space-stack-md`). Never primitives (`--color-brand-600`) in a component, never a raw value (`#5754ed`, `13px`).
- If a token is missing, **do not invent a value**: propose the new token (name + role + value + contrast) in the report and use the closest existing one.

**Components**
- Reuse. Only create a new component if no existing one fits **and** explain why.
- A new variant of an existing component requires a recorded justification (Components section of DESIGN.md).

**Layout and hierarchy** (details: `knowledge/foundations/visual-hierarchy.md`, `knowledge/design-system/spacing-and-layout.md`)
- One `h1` per page. Hierarchy through size/weight/space before color/boxes.
- One primary action per region. Position consistent with screens of the same type (`patterns/actions/action-placement.md`, `patterns/actions/button-hierarchy.md`).
- Spacing only from the scale; group by proximity (Gestalt).
- Running text ≤ 68ch.

**Forms** (`knowledge/foundations/forms.md`)
- Always a visible label; a placeholder never replaces a label.
- Validate on leaving the field or on submit; error next to the field + summary at the top if there are several; never erase what the person typed.
- Do not disable the submit button to "avoid errors" — `patterns/actions/disabled-button.md`.

**Text** — follow `skills/ux-writing/SKILL.md`: buttons with verb + object, errors that say what happened and how to fix it, vocabulary matching the rest of the product, in the project's language.

## 3. Mandatory states

Every surface that receives data or actions implements:

| State | Reference pattern |
|---|---|
| Loading | `patterns/feedback/skeleton-vs-spinner.md`, `patterns/feedback/long-loading.md` |
| Empty (first use, no results, cleared by the user) | `patterns/feedback/empty-state.md`, `patterns/search-filters/no-search-results.md` |
| Error (validation, temporary failure, permission) | `patterns/forms/form-errors.md`, `patterns/feedback/temporary-failure.md`, `patterns/feedback/retry.md` |
| Success | `patterns/feedback/success-confirmation.md`, `patterns/feedback/toast-vs-inline-alert.md` |
| Submission in progress | `patterns/actions/double-submit.md` |
| Interactive: hover, visible focus, active, disabled | `patterns/accessibility/keyboard-focus.md` |

If the project has a dark theme, check both themes.

## 4. Verification before delivery

Run and fix until it passes:

```bash
node <DSX>/tools/lint-raw-values.mjs <changed-folders>     # zero raw values
node <DSX>/tools/contrast.mjs "<text>" "<background>"      # for each new color pair
node <DSX>/tools/lint-design-md.mjs DESIGN.md               # if you changed DESIGN.md
node <DSX>/tools/ux-lint/screen.mjs <capture.html> --ux UX.md   # screen UX gate (T1–T7), on the new capture
node <DSX>/tools/ux-lint/states.mjs <captures> --ux UX.md       # archetype's mandatory states captured (S1–S3)
node <DSX>/tools/lint-ux-md.mjs UX.md                           # if you changed UX.md
node <DSX>/tools/ux-lint/ux-md-drift.mjs UX.md --module <m> --root .   # UX.md still describes the screens (U1–U6)
```

A ux-lint finding of severity ≥ 3 blocks delivery (or becomes registered debt in `.dsx/findings/<module>/` with an owner). Capture with the project's capture skill (DSX's `capture-from-code`, or the project's harness); without a capture, say in the report that the UX gate did not run.

**Changed behavior, update `UX.md` in the same commit.** New or removed screen, archetype, action position, confirmation, feedback, state or flow different from what `UX.md` says: update the screen's row (section 5), the policy or the deviation (`deviations` block + D… table), the map `.dsx/maps/flows-<module>.json` if navigation changed, and bump `version` (policy or archetype → minor; text only → patch) and `updated`. Drift (U5) flags an `updated` older than the screens.

If there is a running app, open the screen (browser or screenshot) and check: 320px width, 200% zoom, keyboard-only navigation (Tab/Shift+Tab/Enter/Esc), dark theme.

Minimum accessibility checklist (full version in `skills/accessibility/SKILL.md`):
- [ ] Every control has an accessible name; an icon without text has `aria-label`.
- [ ] Focus order follows visual order; focus is never hidden.
- [ ] Touch target ≥ 24px (default 44px).
- [ ] Errors communicated by text + icon, not color alone; linked to the field via `aria-describedby`.
- [ ] Important dynamic changes announced (`role="status"` / `role="alert"`).

**Design-system adherence is its own verdict** (Forward `design-system-lifecycle.md`): tokens and kit, semantics, rendered parity, interaction/accessibility and adoption, each pass/fail/unknown with the foundation revision. A clean `lint-raw-values` does not make a screen with poor action topology acceptable, and a good layout does not excuse unexplained drift.

## 5. Delivery report

End with at most 15 lines:

```
Components reused: …
New components/variants (with reason): …
Tokens used: … | Tokens proposed: …
Interaction decisions: <decision> → <pattern>
Archetype: <id> (UX.md <version>) · deviations applied: D… or none
States implemented: loading ✔ empty ✔ error ✔ success ✔ focus ✔ …
Checks: lint-raw-values 0 occurrences · contrast OK · ux-lint no sev ≥ 3 · drift 0 · keyboard OK · 320px OK
UX.md: updated to <version> (what changed) | no behavior change
Pipeline (Forward cycle only): blueprint check <n errors> · criteria pass n / fail n / unknown n · DS adherence <verdict> · critique 6/6
Open items / risks: …
```

For an independent second opinion, ask the `ux-reviewer` subagent to review the screen **without** receiving your reasoning.
